# chub — Notion-style notes app (v1 + v2)

Personal notes app with a Notion-style UI over a SQLite page tree, built as one delivery (v1 + v2).
Stack: pnpm workspace — `web/` (Vite + React + TS + Tailwind v4 + shadcn/ui + editorcn block-editor) and
`server/` (Hono + Drizzle ORM + better-sqlite3). Local-only git repo, Docker for deploy.

### S2 — Stack and packaging (user)

> "Vite + React + TS + Tailwind + shadcn/ui + editorcn, Hono y sqlite con Drizzle + better-sqlite3, vamonos simples y rapidos, pero completos y docker para deploy"

- pnpm workspace with exactly two packages: `web/` and `server/`.
- `web/`: Vite + React + TypeScript + Tailwind CSS v4 + shadcn/ui + editorcn (installed via the shadcn registry, so the editor source is vendored into the repo).
- `server/`: Hono + Drizzle ORM + better-sqlite3, TypeScript, run with `tsx` in dev.
- Tailwind v4 (CSS-first config, `@tailwindcss/vite`), not v3.
- Docker for deploy, with the SQLite file and uploads on a `./data` bind mount.
- "simples y rapidos, pero completos": no speculative abstraction layers, no ORM magic beyond Drizzle, no state library beyond React Query-free plain fetch hooks unless a task proves it needed.

### S3 — No auth, no Supabase, local SQL (user)

> "me gusta la A, pero no quiero estar ligado a supabase, por ahora no quiero auth y estaria bien con sql"

- No authentication, no users table, no sessions, no login UI, no multi-tenancy.
- No Supabase, no Postgres, no Neon. One local SQLite file.
- The app is single-user by design. Do not add an owner/user column to satisfy a hypothetical future.

### S4 — Data model (decision, memory obs #3169)

> Hierarchy lives in the DB, NOT the filesystem: self-referencing `pages(id, parent_id NULL, title, content JSON = Tiptap doc, position, created_at, updated_at, deleted_at)`

- Exactly one table, `pages`, with those columns. Nothing else.
- Hierarchy is in the DB. There are no real folders, no vault directory, no files-on-disk notes.
- A "folder" is simply a page that has children **and** its own content. Depth is unlimited.
- Sibling order is `position`. Soft delete is `deleted_at`.
- Tree read: fetch all page metadata (no `content`) in one query and build the tree on the client.
  Do not write `WITH RECURSIVE` or any recursive CTE now.
- **Non-goal for this delivery:** the future Books section. Do not create a `books` table, do not add a `book_id` column, do not build a Books UI. The only thing that keeps that door open is `parent_id` + `content` as JSON.

### S9 — API contract (frozen — `web/` and `server/` are built against this in parallel)

Shared types:

```ts
type PageMeta = { id: string; parentId: string | null; title: string; position: number; updatedAt: string; deletedAt: string | null };
type Page = PageMeta & { content: unknown }; // content is a Tiptap JSON doc
```

- `id`: `crypto.randomUUID()`. Timestamps: ISO-8601 UTC strings. Errors: `{ "error": "<code>" }` with a matching HTTP status.

| Method + path | Request | Success | Errors |
| --- | --- | --- | --- |
| `GET /api/pages/tree` | — | `200 { pages: PageMeta[] }` — all **non-deleted** pages, no `content`, ordered by `(parentId, position)` | — |
| `GET /api/pages/trash` | — | `200 { pages: PageMeta[] }` — all soft-deleted pages | — |
| `GET /api/pages/:id` | — | `200 Page` | `404 page_not_found` |
| `POST /api/pages` | `{ parentId?: string \| null; title?: string; position?: number }` | `201 Page` — `title` defaults to `""`, `content` defaults to an empty Tiptap doc, `position` defaults to the end of the sibling list | `400 parent_not_found` |
| `PATCH /api/pages/:id` | `{ title?: string; content?: unknown }` | `200 Page` | `404 page_not_found` |
| `POST /api/pages/:id/move` | `{ parentId: string \| null; position: number }` | `200 { pages: PageMeta[] }` — every sibling row whose `position` changed, including the moved page | `404 page_not_found`, `400 parent_not_found`, `400 cannot_move_into_descendant` |
| `DELETE /api/pages/:id` | — | `200 { deleted: string[] }` — ids of the whole soft-deleted subtree | `404 page_not_found` |
| `POST /api/pages/:id/restore` | — | `200 { restored: string[] }` — ids of the whole restored subtree | `404 page_not_found` |
| `DELETE /api/pages/:id/purge` | — | `200 { purged: string[] }` — ids of the whole hard-deleted subtree | `404 page_not_found` |
| `GET /api/search?q=` | query | `200 { results: { id: string; title: string; snippet: string }[] }`; a missing or blank `q` returns `200 { results: [] }`; only **non-deleted** pages are searchable, so trashed pages never appear in results; arbitrary user input (quotes, operators, unbalanced syntax) must NEVER produce a 5xx — it is sanitized into a safe query, and input that sanitizes to nothing searchable simply returns `200 { results: [] }`; results are ranked by relevance and capped at 20 | — |
| `GET /api/pages/:id/export.md` | — | `200` `text/markdown; charset=utf-8`, `Content-Disposition: attachment; filename="<sanitized title>.md"`; an empty or whitespace-only title becomes `untitled.md`; a soft-deleted page IS still exportable by explicit id, because the trash is how a user recovers content, so this endpoint deliberately does NOT filter on `deleted_at` (contrast the search row); unknown or future block types degrade to their text instead of failing | `404 page_not_found` |
| `POST /api/uploads` | multipart, field `file` | `201 { url: string; mime: string; width: number \| null; height: number \| null }`; `width`/`height` are reported ONLY when the file is structurally valid enough to actually contain them — a truncated, malformed or polyglot file yields `null` rather than numbers read from bytes that do not form a real image; exactly 10 MB is accepted, anything larger is rejected | `400 unsupported_media_type` (not an image), `413 payload_too_large` (> 10 MB) |
| `GET /uploads/:name` | — | `200` the stored bytes with the sniffed image `Content-Type` and `X-Content-Type-Options: nosniff` — these are user-controlled bytes served from the app's own origin, so the browser must never be allowed to re-interpret them as HTML | `404` for an unknown, path-like, encoded or double-encoded name |

### S10 — Server invariants (must hold on every write)

1. Moving a page into itself or into any of its own descendants fails with `400 cannot_move_into_descendant` and leaves the tree byte-identical.
2. Sibling `position` values are 0-based and contiguous within each parent after every create, move, delete, restore and purge.
3. Deleting a page soft-deletes its entire subtree (`deleted_at` set on all of them); restore clears `deleted_at` on exactly the same subtree; purge hard-deletes exactly that subtree.
4. `deleted_at` on a child whose ancestor is deleted is not "extra deleted": restore of the ancestor restores exactly the rows it deleted.
5. Every mutating endpoint returns only the rows it actually changed, and returns an empty array rather than `null` when nothing changed.
6. No endpoint ever writes a partial tree: each mutating request runs inside a single SQLite transaction.

### S11 — Autosave contract (v1)

- The editor debounces saves **700 ms** after the last edit.
- Indicator states, in English UI copy, forming one ordered sequence: `Idle` while the page has never been edited, `Unsaved` from the first edit until a save is actually in flight (the debounce window must NEVER be shown as `Idle`), `Saving…` while a PATCH is in flight, `Saved` after a successful PATCH, `Save failed` after a failed one.
- A failed save must be retried by the next debounce window; it must never silently drop the edit.
- Navigating away from a page with a pending debounce flushes the save immediately (no lost last edit).
- The title autosaves under the same contract.

### S12 — Trash (v2)

- A `Trash` entry in the sidebar lists soft-deleted pages.
- Restore returns the page to its original position in the tree (or to the root if its parent is still deleted).
- "Delete permanently" purges the subtree and **must** require an explicit confirm step in the UI, because purge is irreversible.

### S13 — Deploy (user)

> "docker para deploy"

- One production image: the built `web/` static assets are served by the Hono server, so it is one container and one port.
- `docker compose up` starts it; `./data` is bind-mounted and holds the SQLite file **and** uploaded images.
- The app must run with an empty `./data` directory on first boot (migrations apply themselves at startup).
